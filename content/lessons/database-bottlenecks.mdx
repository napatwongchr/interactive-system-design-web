Your app was fast at 10 users. At 1,000 users it's suddenly slow. The server looks fine — CPU is low, memory is fine. But responses take 3 seconds.

You add some logging. Every request is spending almost all its time... waiting for the database.

The database is the bottleneck. It almost always is.

## Why the Database Struggles First

Your server is stateless — you can run ten copies of it. Your database is stateful — there's one, and it has a fixed amount of resources it can apply to queries.

At 1,000 users, 1,000 requests are all hitting that one database simultaneously. Most of those requests need data. The database is handling queries as fast as it can, but the queue grows.

## The Three Database Killers

### 1. Slow Queries

A query that does a full table scan is fine at 1,000 rows. At 5 million rows, it takes seconds. Multiply by 1,000 concurrent users and you're done.

The fix is **indexing** — you'll learn that in Chapter 4. For now, know that unindexed queries on large tables are the single most common cause of database slowdowns.

### 2. The N+1 Problem

This one is sneaky. Your ORM makes it easy to write:

```typescript
const posts = await db.posts.findMany()          // 1 query
for (const post of posts) {
  const author = await db.users.findById(post.authorId)  // N queries
  // ...
}
```

That's `1 + N` queries — one to get the posts, then one per post to get the author. For a page showing 50 posts, that's 51 database round trips instead of 1.

AI-generated code does this a lot. Look for `findMany()` calls inside loops.

The fix: use `include` or `join` to fetch related data in one query.

### 3. Connection Pool Exhaustion

As shown above: your pool has a fixed size. When it's full, every new query waits. If queries are slow, the pool stays full longer. A feedback loop begins.

The fix: faster queries (fewer connections needed at once) + caching (fewer queries overall).

## How to Find the Problem

If you're on Postgres, run `EXPLAIN ANALYZE` before a slow query. It shows you exactly what the database did:

- **Seq Scan** on a large table = no index, it read every row
- **cost** numbers = relative expense of each operation
- **actual time** = how long it actually took

The first Seq Scan on a large table is usually your smoking gun.
