You click "Save." A spinner appears, then your item shows up in the list.

That took maybe 200 milliseconds. In that time, your click traveled from your browser across the internet, hit a server, was validated, turned into a database query, saved to disk, and the confirmation traveled back — all before you finished reading this sentence.

Let's trace it step by step.

Here's what each step actually means:

1. **Your React component** calls `fetch('/api/items', { method: 'POST', body: ... })`. That's the browser sending an HTTP request to your backend.
2. **Your API route** (an `app/api/items/route.ts` file or an Express handler) receives the request, reads the body, and validates it. If the data looks wrong, it sends back a `400 Bad Request` and stops here.
3. **The API route runs a query** — something like `db.insert(items).values(...)` — against the database.
4. **The database** writes a new row and returns the ID of the new record.
5. **The API route** wraps that ID and the saved data into a JSON response and sends `200 OK` back to the browser.
6. **Your React component** receives the response, updates state, and re-renders. The spinner disappears. Your item appears.

## What the AI Generated, Explained

You probably have files you've never fully read. Here's what they actually do:

**Route handlers** (`app/api/*/route.ts` or `pages/api/*.ts`) — These are your backend. Each file handles HTTP requests to a specific URL. The AI created one for every CRUD operation your app needs.

**ORM queries** (`db.select()`, `prisma.user.findMany()`, etc.) — These are your database calls. An ORM (Object-Relational Mapper) is a library that translates JavaScript objects into SQL queries. You write JavaScript; it writes SQL.

**Environment variables** (`DATABASE_URL`, `NEXTAUTH_SECRET`, etc.) — These are secrets and configuration values stored outside your code. On your machine they live in a `.env.local` file. In production they're set on the server. They never get committed to Git.

## "It Works on My Machine"

The most common confusion when you first deploy: everything worked locally, now it's broken.

Here's why: on your machine, all three layers run together. Your browser, your API routes, and your database are all on the same computer, often all in the same terminal process.

In production, they're separate:
- Your frontend is probably served from a CDN (a network of servers around the world)
- Your API runs on a server in one specific location
- Your database is its own managed service somewhere else entirely

They communicate over the network — the same HTTP protocol you just learned about. When your app breaks in production, it's usually because one of these connections isn't configured correctly (wrong `DATABASE_URL`, missing environment variable, CORS policy blocking requests).

## Serverless Functions Are Still Backends

If your app uses Vercel Functions, AWS Lambda, or Next.js App Router server components, you're using **serverless functions** — backend code that runs on demand instead of on a permanently-running server.

Same three-layer model. Same HTTP protocol. Just a different deployment style. The function starts when a request arrives, handles it, and then stops. The database is still separate, still persistent, still the source of truth.

Your mental model doesn't change.
