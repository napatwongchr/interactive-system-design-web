You're looking at your monitoring. CPU is at 95%. Memory is at 87%. New requests are timing out.

Your server isn't broken — it's just full.

Every server has finite resources, and understanding what those resources are tells you exactly what's happening when things go wrong.

## CPU

The CPU executes your code. More requests = more code executing = more CPU usage.

Node.js is single-threaded: it can only run one piece of JavaScript at a time. It handles many requests by switching between them quickly during I/O waits — "I'm waiting for the database, let me handle this other request while I wait."

This works brilliantly for I/O-bound code (database queries, HTTP calls). It breaks down for **CPU-bound code**: resizing images, parsing huge JSON files, running complex algorithms. Those operations block the thread. While your server resizes one image, 50 other requests pile up waiting.

**The fix:** offload CPU-heavy work to background jobs (you'll learn this in Chapter 4).

## Memory

RAM stores your active work: request data, cached values, open connections, in-progress operations.

Every concurrent request consumes some memory. If 500 users are simultaneously loading a page that serves 2MB of data each, that's 1GB of active data in RAM. If your server only has 512MB, it crashes.

Memory leaks are sneaky: code that holds references to objects it no longer needs. Your app might handle 1,000 requests just fine but crash after 10,000 because memory is accumulating that never gets freed.

**The fix:** monitor memory over time, not just at peak. Restart workers periodically in production if you suspect leaks.

## Connections

Database connections are the most commonly exhausted resource.

Your server maintains a **connection pool** — a fixed set of open connections to the database, typically 10–100. Each active query needs one connection. If all connections are in use, new queries wait.

At 1,000 concurrent requests, each waiting for a database response, your 20-connection pool has 20 queries running and 980 waiting. The waiters keep arriving. The pool never empties. Everything grinds to a halt.

**The fix:** cache repeated queries so fewer hit the database. Use connection poolers like PgBouncer for high-concurrency workloads.

## The Node.js Rule

Servers excel at I/O-bound work. They're bad at CPU-bound work.

Design your API routes to be thin: receive a request, query the database, return a response. Don't do heavy computation in the request handler. Your database can handle that better — or hand it off to a background job.

If your endpoints are slow and the database looks fine, the bottleneck is probably CPU. If everything is slow and queries are fast, it's probably memory or connections.
