It's 11pm on a Tuesday. Your app was featured on a newsletter that went out to 50,000 people. 1,000 of them opened it at the same time.

Your phone starts buzzing. "Is your site down?" "Getting a 502." "Mine just says 'Error'."

Something broke. But what?

## The Order of Failure

When traffic spikes, systems don't fail randomly. They fail in a predictable order. Knowing that order tells you where to look first.

Step 1: 1,000 users hitting your app. Step 2: Your server relays all those requests to the database. Step 3: External APIs hit their rate limits and start refusing.

## What Usually Breaks First: The Database

Almost always, the first thing to crack is the database.

Your server is relatively scalable — it handles requests fast and moves on. But the database has a fixed connection pool, usually 10–100 connections.

At 10 users, no problem. At 1,000 simultaneous users, 900 are waiting for a connection to free up. Queries that took 5ms now take 2 seconds because they're queued. Your server times out waiting. Users see errors.

## What Breaks Second: Memory

Each open request holds data in memory — the request body, session data, in-progress work. At 1,000 concurrent requests, your server might be holding 200MB of data in RAM.

If you only have 256MB, you're dead. The process crashes and restarts, dropping every in-flight request.

## What Breaks Third: CPU

If your server does heavy work per request — parsing large JSON payloads, resizing images, running complex calculations — 1,000 simultaneous requests will peg the CPU at 100%.

Everything slows to a crawl. Responses that took 20ms now take 30 seconds.

## How to Read the Signs

| Symptom | Most likely cause |
|---------|------------------|
| Slow responses that keep getting slower | Database connection pool exhausted |
| Server crashes and restarts | Out of memory |
| 429 errors from external services | Rate limit hit |
| Timeouts on one specific endpoint | That endpoint has a slow query |
| Everything fine, then sudden crash | Memory leak accumulated under load |

## The Good News

These failure modes are well-understood. Every scaling technique you'll learn in the next chapters — caching, indexing, load balancing, async queues — addresses one of them specifically.

Knowing what breaks first means you know what to fix first. You don't need to guess.
