A user signs up for your app. The signup form submits. Two seconds later, the page finally loads.

Two seconds is an eternity. Users expect 200ms. Where did those 2 seconds go?

You look at the code. After saving the user to the database (fast), your server sends a welcome email, resizes their profile picture, and updates an analytics summary. Each one takes 400–600ms. They all run one after another.

The user waited while your server did work they couldn't see and didn't need before continuing.

That's what async operations fix.

## Synchronous vs Asynchronous

**Synchronous**: do everything before responding. The user waits for all of it.

**Asynchronous**: do the minimum required, respond immediately, finish the rest in the background.

## What to Move Off the Request Path

Ask yourself: does the user need this to happen before they see the next screen?

**No — move to background:**
- Sending welcome emails or notifications
- Resizing or processing uploaded images
- Generating PDF reports or data exports
- Syncing data to external services (analytics, CRMs)
- Anything that calls a slow external API

**Yes — keep synchronous:**
- Saving the user's input to the database
- Validating the request
- Checking permissions
- Returning the result they're directly waiting for

## The Job Queue Pattern

A **job queue** is a list of pending background tasks, usually backed by Redis.

Your server adds jobs to the queue. One or more **workers** (separate processes) read from the queue and execute the jobs.

If a job fails (email service is down), the queue retries it automatically — after 1 minute, then 5 minutes, then 30 minutes. You don't silently drop work.

If your workers are overloaded, jobs pile up in the queue rather than crashing your server. The queue acts as a buffer.

## Tools for Node.js

- **BullMQ** — Redis-backed, mature, feature-rich. Good default choice.
- **Inngest** — serverless-friendly, great for Next.js apps. Jobs defined as functions.
- **Trigger.dev** — built for developer experience, with a dashboard for monitoring jobs.

Pick one that matches your deployment style. If you're on Vercel, Inngest fits well. If you have a persistent server, BullMQ with Redis.

## The Two-Second Problem, Fixed

With async jobs: save user to DB (20ms) → enqueue welcome email job (5ms) → respond (25ms total).

The user sees the confirmation page in under 100ms. The email arrives in their inbox 3 seconds later. Nobody is waiting on nobody.
