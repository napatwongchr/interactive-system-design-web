You've set up four servers behind a load balancer. Traffic is distributed. Things are fast.

Then users start reporting a bug: they get logged out randomly. Sometimes mid-session. They log back in, it works for a while, then happens again.

You investigate. The problem: your app stores session data in each server's memory. When a user logs in on Server 1, Server 2 and 3 and 4 have no idea. Next request goes to Server 3 — logged out.

This is the stateful server problem.

## Stateful vs Stateless

**Stateful server** — remembers things between requests. User sessions, in-flight calculations, local caches. Works fine with one server. Breaks badly when you have multiple.

**Stateless server** — every request contains everything needed to process it. The server remembers nothing between requests. Any server can handle any request.

Step 1: User makes a request. Step 2: Load balancer sends it to any available server. Step 3: Both servers check Redis for the session — same data, regardless of which server handles the request.

## The Fix: Move State Out of the Server

Every piece of state your server currently holds in memory needs to move somewhere shared.

| What | Where to move it |
|------|-----------------|
| User sessions | JWTs in the client, or Redis |
| Uploaded files | S3 or object storage |
| Background job state | Database or Redis |
| Rate limiting counters | Redis |
| In-memory caches | Redis |

The pattern: your servers become **disposable**. Kill one, spin up another — nothing is lost. Redis and your database hold the truth.

## JWTs: The Stateless Session

A **JWT** (JSON Web Token) is a signed token stored in the browser. It contains: "this is user #42, they logged in at this time, the token expires at this time."

The server doesn't need to look anything up — it reads the JWT, verifies the signature, and knows who the user is. No database query, no Redis lookup, no shared state.

The trade-off: you can't immediately invalidate a JWT. If a user changes their password, their old JWT still works until it expires. For most apps, this is fine. For security-critical flows (password reset, account compromise), you pair JWTs with a short-lived token blocklist in Redis.

## Why This Makes Scaling Easy

A stateless server can be:

- Added instantly (just start a new one and add it to the load balancer)
- Removed instantly (drain its active connections, shut it down — nothing is lost)
- Replaced during deployment (update one at a time with zero downtime)
- Run in any data center (no sticky sessions, no geographic constraints)

Statelessness is what makes auto-scaling possible. When traffic spikes, your cloud provider can spin up new instances in seconds. When it drops, it shuts them down. Your app doesn't care.
