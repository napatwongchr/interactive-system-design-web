You've split your app into services. The order service calls the notification service to send a confirmation email. Simple enough.

Then the notification service goes down for 10 minutes during a deployment.

During those 10 minutes, every order fails — not because the order itself was wrong, but because the notification call failed. Customers lose their orders. You lose revenue.

This is what happens when services call each other directly. A queue fixes it.

## The Problem with Direct Calls

When Service A directly calls Service B:

- If B is slow, A is slow
- If B is down, A fails
- If B is overwhelmed, A backs up
- A and B are **tightly coupled**: problems in B become problems in A

## How It Works

The order service **publishes** a message: `{ type: "order-placed", orderId: 4521, userId: 42 }`.

That's it. The order service's job is done. It doesn't wait. It doesn't care what happens next.

The notification service **subscribes** to messages of type `order-placed`. When it reads one, it sends the email.

If the notification service is down, the message sits in the queue. When it comes back up, it reads all the queued messages and processes them. Zero orders lost.

## Key Properties

**Durability** — messages are stored on disk, not in memory. Even if the queue server restarts, your messages survive.

**At-least-once delivery** — the queue guarantees a message will be delivered at least once. (Sometimes it delivers it twice if something goes wrong mid-processing.) Your consumer needs to handle duplicates — called **idempotency**.

**Backpressure** — the queue absorbs traffic spikes. If 10,000 orders come in at once and your notification service handles 500/minute, the messages pile up safely in the queue. Everything eventually gets processed.

## Common Use Cases

- Order and payment confirmations
- Sending emails, SMS, and push notifications
- Image and video processing
- Webhook delivery to external services
- Syncing data between systems
- Any work you'd put in an async background job

## When to Use a Queue vs a Background Job

The distinction is subtle:

**Background jobs** (BullMQ, Inngest) — work within your own system. "Do this thing later."

**Message queues** (RabbitMQ, SQS, Kafka) — communication between separate services. "Tell that other system that this happened."

For most apps, a background job system is enough. You reach for a full message queue when you have genuinely separate services that need to communicate.

## Tools

**Redis + BullMQ** — the most common Node.js choice. Redis stores the queue, BullMQ handles retries, priorities, and delayed jobs.

**AWS SQS** — managed queue that scales automatically. Zero infrastructure to maintain.

**Kafka** — high-throughput event streaming for massive scale. Overkill unless you're handling millions of events per second.
