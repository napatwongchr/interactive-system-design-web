Your app has 10,000 users. The front page shows the top 10 posts. Every time someone loads it, your server runs the same query: `SELECT * FROM posts ORDER BY likes DESC LIMIT 10`.

That's 10,000 identical database queries per day — all returning the same result, since the top posts don't change that often.

What if you just... saved the answer?

## The Core Idea

**Caching** stores the result of an expensive operation so you don't have to repeat it.

The first user who loads the top posts triggers the database query. You save the result. The next 9,999 users get the saved result instantly — no database involved.

Step 1: User makes a request. Step 2: Cache has the answer — return immediately (cache hit). Step 3: Cache doesn't have it — query the database (cache miss). Step 4: Store the result in cache for the next request.

## Where to Cache

**In-memory** — stored in your server's RAM. The fastest option. Lost on restart. Good for data that can be recomputed cheaply. Bad when you have multiple servers (each has its own cache).

**Redis** — a dedicated cache server, separate from your app. Shared across all your server instances. Survives restarts (sort of — Redis can be configured for persistence). The standard production choice.

**HTTP Cache-Control headers** — tell browsers and CDNs to cache responses without any server-side code:

```
Cache-Control: public, max-age=300
```

This one is free and requires zero infrastructure. Use it for anything that doesn't change per-user.

## The Hard Part: Invalidation

"There are only two hard things in computer science: cache invalidation and naming things." — Phil Karlton

The question is: when the data changes, how do you update the cache?

**TTL (Time-To-Live)** — cache entries automatically expire after N seconds. Simple. The data might be stale for up to N seconds. Acceptable for most things.

**Explicit invalidation** — when you write to the database, immediately delete the relevant cache entry. It gets regenerated on the next request. Always fresh. More code to maintain.

**Cache-aside** — the most common pattern: check cache first, on miss fetch from DB and populate cache. Your code does both operations explicitly.

## What Not to Cache

Some things should never be cached:

- **User-specific data** without keying by user ID (user A sees user B's profile)
- **Financial data** that must be real-time accurate
- **Write operations** — only cache reads
- **Small datasets** that are fast to query anyway (adds complexity for no gain)

Start with caching your most-queried, least-frequently-changing data. The top posts list. The product catalog. Public profile pages. You'll feel the impact immediately.
