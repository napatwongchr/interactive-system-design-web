Your app loads user profiles. At 100 users, profiles load in 5ms. At 100,000 users — with 100,000 rows in the database — the same query takes 2 seconds.

Nothing changed in your code. The query is the same. But the database is working much harder.

The fix is one SQL statement. Here's why.

## What the Database Is Doing Without an Index

When you run:

```sql
SELECT * FROM posts WHERE user_id = 42
```

Without an index on `user_id`, the database reads every single row in the `posts` table to find the ones where `user_id = 42`. This is called a **sequential scan** (or full table scan).

At 100 rows: no problem. At 10 million rows: the database reads 10 million rows to find maybe 50.

## Adding an Index

```sql
CREATE INDEX idx_posts_user_id ON posts(user_id);
```

That's it. The database builds a sorted data structure on `user_id` — think of it as the index at the back of a book. Now the query jumps directly to the matching rows instead of reading all of them.

Your ORM can do this too:

```typescript
// In a Prisma migration
model Post {
  id     Int @id
  userId Int
  // ...
  @@index([userId])
}
```

## The Trade-off: Indexes Slow Down Writes

Every index you add speeds up reads and slows down writes.

When you insert, update, or delete a row, the database must update every index on that table. A table with 5 indexes does 6 operations per write (1 row + 5 index updates).

For read-heavy apps (most web apps), this trade-off is worth it. But don't add indexes speculatively — add them when you've identified a slow query.

## Finding Slow Queries

Run `EXPLAIN ANALYZE` before any query you're investigating:

```sql
EXPLAIN ANALYZE SELECT * FROM posts WHERE user_id = 42;
```

Look for **Seq Scan** on large tables. That's your target. Add an index on the column being filtered, re-run, and watch it become an **Index Scan**.

## Which Columns to Index

Index columns that you frequently filter by:

- Foreign keys (`user_id`, `post_id`, `order_id`) — almost always worth indexing
- Columns used in `WHERE` clauses in hot queries
- Columns used in `ORDER BY` on large tables

The primary key is already indexed automatically. You don't need to add that one.
